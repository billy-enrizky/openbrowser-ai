## 2. How to read this page

A fixture is a local test page with a deterministic expected result. The native lanes use fixtures. A run passes only when the product returns the required result, so every latency number has a correctness check behind it.

| Term | Meaning |
| --- | --- |
| p50 (median) | The middle sample. Half the runs were faster and half were slower. |
| Cold start | Every task starts a fresh process tree, including the daemon or server and the browser. |
| Warm | The browser is already open. Each task gets a fresh fixture page and reuses the browser. |
| No-browser | No Chromium, Blink, or V8 process. The tool fetches over HTTP and parses the response. JavaScript does not run. |
| RSS | Resident set size: physical memory held by the process tree at the sample time. Shared pages can be counted more than once. |
| Pair | One sample from each arm on the same task and sample index. A 5 of 5 result means OpenBrowser was faster in all five pairs. |
| N | The number of samples per arm and task. |

For task time and memory, lower is better. Charts and tables that measure them carry a down arrow and the label **Lower is better**. If a chart shows a metric where higher is better, it says **Higher is better** with an up arrow.

These interactive figures describe the configured native workflows. OpenBrowser permits automatic local engine selection, while the other framework adapters select system Chrome explicitly. Complete executable bindings are required for a matched-engine comparison.

## 3. Current interactive lanes, 2026-11-27

These lanes use seven interfaces: OpenBrowser MCP, OpenBrowser CLI, Chrome DevTools MCP, agent-browser CLI, browser-use CLI, Playwright MCP, and Playwright CLI. Every task runs against a local fixture with an exact oracle. Each cell has N=5, and the arm order rotates between samples.

The cold lane measures five tasks and records 175 latency and 175 valid resource observations. The warm lane measures four tasks and records 140 latency and 140 valid resource observations. All 630 observations passed the oracle, keychain, engine, and cleanup checks. One machine and one pinned browser serve every arm: Chrome for Testing `159.0.8154.6`, revision 1255. OpenBrowser app `0.1.61.dev173+g9f630f7c6` starts at digest `847bbf45`.

### 3.4. WebMCP page tools, capability check

Pinned Chrome `159.0.8154.6` exposes `document.modelContext` when it starts with `--enable-features=WebMCP`. Without the flag, the document object and the `navigator` alias are absent. With the flag, the document object provides `getTools`, `executeTool`, and `registerTool`, and `navigator.webmcp` stays absent. The browser version requires the flag.

The capability check runs two tasks on four surfaces: OpenBrowser CLI `-c`, OpenBrowser MCP `create_context` and `execute_code`, Playwright CLI, and Playwright MCP. All eight task oracles pass. The page registers one tool with an exact name, description, and input schema. Discovery returns that catalog. Invocation with 17 and 25 returns `{"content":[{"type":"text","text":"42"}]}`.

This check is a page-API bridge. The fixture registers tools through the page API, and each surface calls them through its native scripted page API. Dedicated WebMCP commands are outside the pinned interfaces. This section reports capability only and makes no latency or memory claim. The five interactive tasks stay unchanged.

Runner: [webmcp_capability.py](https://github.com/billy-enrizky/openbrowser-ai/blob/main/benchmarks/interactive/webmcp_capability.py). Focused tests: [test_webmcp_capability.py](https://github.com/billy-enrizky/openbrowser-ai/blob/main/tests/test_webmcp_capability.py). Run the runner without arguments to print the inert plan. `--run-output` with the four browser binary paths runs the check. Default and flag probes are private evidence, and the runner reproduces them with `--without-feature`.

```bash
openbrowser-ai scrape https://example.com --text-only --only-main-content
openbrowser-ai --render-mode full --no-css --no-images -c "await navigate('https://example.com')"
```

### 5.5. Discovery: map and crawl

Firecrawl users build site pipelines on `map` and `crawl`. OpenBrowser has both, and neither starts a browser.

```bash
openbrowser-ai map https://docs.example.com --max-urls 50 --exclude '\.pdf$'
openbrowser-ai crawl https://docs.example.com --max-pages 20 --max-depth 2
```

`map_urls` reads the page, `/sitemap.xml`, and one sitemap index level, then normalizes, deduplicates, and filters by origin, include, and exclude patterns. `crawl_site` follows same-origin links breadth first, fetches each page once, parses it once, and returns page content plus a per-page link count.

Limits: both use the OpenBrowser no-browser path. A JavaScript shell page is reported as failed or skipped. This section reports pass or fail for each mode and gives no timing result.

## 6. Why OpenBrowser is faster and more efficient

The measured paths use four areas of work. Each area maps to a lane on this page.

| Area | Mechanisms in the measured paths | Measured lane |
| --- | --- | --- |
| Request grouping and state reuse | Group several browser actions into one Python request, load optional libraries on first use, and use a small warm CLI client over standard-library IPC | Warm and cold interactive lanes |
| Lean MCP entry | Serve `tools/list` from a generated catalog, keep stateful application setup lazy, and use a direct path for stateless tools | Cold and warm MCP lanes |
| Strict HTTP | Fetch and parse static pages in a Python process, with a pooled batch client and bounded concurrency for CLI and namespace batches | Firecrawl Local batch and no-browser memory lane |
| Targeted browser work | Use selector and CDP helpers for known targets, and block selected asset types in lightweight and no-render policies | Warm and cold interactive lanes and render asset lane |

OpenBrowser 0.1.61 also provides a native warm-code CLI frontend on compatible platform wheels. The [CLI frontend reference](/customize/integrations/native-cli) explains the command boundary and explicit Python option. Each result artifact identifies its measured application build.

### 6.1. What each area changes

1. **Request grouping and state reuse.** The interactive MCP and CLI arms group several browser actions into one Python request for most tasks. The `auth` task uses a login program and an account program around the browser restart. A request can hold several actions and persistent variables. The namespace loads optional libraries on first use. Warm CLI calls use a small standard-library client over IPC, and cold CLI startup loads the full client.
2. **Lean MCP entry.** The lean stdio transport reads generated definitions for discovery. Stateful application setup stays lazy, and stateless tools use a direct path. The SDK escape hatch uses a different import path. Stateful task startup still includes browser and application work.
3. **Strict HTTP.** Explicit `--no-browser` and `engine="http"` fetch and parse static pages in a Python process. CLI and namespace batches reuse one pooled HTTP client with bounded concurrency. The stateless MCP `scrape_web` call creates a one-shot client per call.
4. **Targeted browser work.** Task scripts use selector and CDP helpers for known targets, which avoids a full DOM scan for those operations. Lightweight and no-render policies block selected asset types. The browser still loads Chromium, Blink, and V8. Indexed actions remain the general path for changing pages, and download and new-tab helpers keep their browser interaction.

### 6.2. Scope

Other frameworks also reuse sessions and batch work. These lanes measure the configured combination. The page assigns no causal share to one mechanism without an ablation. The Firecrawl Local batch uses a 10 ms job-poll workflow and returns markdown pages; OpenBrowser returns selected row dictionaries. The no-browser memory lane measures OpenBrowser on one local fixture. A matched single-call Firecrawl Local memory lane remains open, as do model-driven Agent and CodeAgent lanes and matched Lightpanda cold and warm lanes.

## 7. How to choose a surface

| Need | Use | Why |
| --- | --- | --- |
| One static page, no browser | `openbrowser-ai scrape URL --no-browser` or MCP `scrape_web` | No Blink or V8. JavaScript does not run. See the no-browser memory section. |
| Many known URLs | `openbrowser-ai scrape --no-browser --jsonl` | Concurrent no-browser fetches. |
| Site discovery | `openbrowser-ai map URL` | Page links plus sitemap. No browser. |
| Site-wide text | `openbrowser-ai crawl URL` | Bounded breadth-first crawl. No browser. |
| JavaScript page, one shot | `openbrowser-ai scrape --engine browser` | Headless shell path. |
| Long interactive session | MCP `create_context` plus `execute_code` | Lowest measured warm p50 on every task. |
| One-off interactive command | `openbrowser-ai -c` | No server to manage. |
| Visual work | `--render-mode full` | Screenshots and real paint. |
