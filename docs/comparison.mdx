# Browser Automation Comparison

This page combines historical benchmark runs with current native local lanes:

1. **[CLI Benchmark](/cli-comparison)** (2026-03-15) -- 4-way comparison of CLI tools driven by an LLM via a single Bash tool
2. **MCP Benchmark** (below) -- 3-way historical comparison of MCP servers as tool providers
3. **Native local lanes** (2026-11-24) -- scraping, lightweight, interactive cold, and interactive warm benchmarks with raw JSONL evidence

> **Historical benchmark, not a current-version ranking.** The two MCP runs below were recorded on the dates shown. The 6-task LLM run installed Playwright MCP and Chrome DevTools MCP from `@latest` at run time, but their resolved versions were not written to the retained artifacts. The 5-step run's install method was not retained. The 5-step token benchmark's raw per-response files are also not retained in this repository. Treat these numbers as historical observations for the versions installed on the run date, not as a comparison against today's releases. No universal winner follows from them. See [Provenance and limits](#provenance-and-limits).

## Native local benchmark lanes, 2026-11-24

These local fixture runs use no LLM, cloud browser, or AWS. They measure different workloads, so they do not produce one product ranking. The raw data and methods live in `benchmarks/scraping/README.md` and `benchmarks/interactive/README.md`.

### What these lanes show

OpenBrowser is the faster local scraping tool overall. It wins three of five tasks against Firecrawl Local. Static article is parity. The largest wins are 20.7x on the JavaScript list, 19.1x on the asset-heavy page, and 2.09x on table extraction. Firecrawl leads pagination by 7 percent. Against Lightpanda, OpenBrowser no-render is faster on all five tasks, but Lightpanda uses far less memory.

In the prior warm run, the CSS selector arm beat chrome-devtools-mcp on all four tasks, beat browser-use on two tasks, and beat agent-browser on two tasks. Download against browser-use was parity. Browser-use won tabs, and agent-browser won download and tabs. The direct popup helper lowers OpenBrowser's local tabs p50 against its prior path. Its competitor result remains exploratory. The semantic helper arm remains separate.

The fixtures do not test live-site anti-bot behavior, CAPTCHA, or login providers. The resource lane measures RSS and CPU, not GPU memory, disk I/O, or energy. Lightpanda and Chromium use different engines and do not have identical layout, paint, extension, or screenshot behavior. Local fixture results do not establish a ranking for live websites.

### Why the Difference

| Design Decision | Playwright MCP | Chrome DevTools MCP | OpenBrowser MCP |
|----------------|---------------:|--------------------:|----------------:|
| Navigate response | Full a11y snapshot | URL confirmation | URL confirmation |
| State query | Always full snapshot | Full a11y snapshot (`take_snapshot`) | Compact (105 tokens) or full |
| Click response | Updated snapshot | Action confirmation | Action confirmation |
| Text extraction | No dedicated tool | No dedicated tool | `evaluate()` + Python processing |
| Content search | Dump full snapshot | `evaluate_script` (JS) | `evaluate()` + Python regex/string matching |
| Element search | Part of snapshot | `uid` from snapshot | `browser.get_browser_state_summary()` |

**Playwright MCP**: Every navigation returns the full page accessibility snapshot (~124K tokens for Wikipedia). Consistent, but forces the LLM to process the entire page with every action.

**Chrome DevTools MCP**: Returns minimal confirmations for navigation. The agent must explicitly call `take_snapshot` to see the page (~135K tokens for Wikipedia). One snapshot is comparable in size to Playwright's, but actions don't auto-return snapshots.

**OpenBrowser MCP**: Actions return minimal confirmations. The agent explicitly requests the level of detail it needs -- from 105 tokens (compact state) to 3,981 tokens (targeted search) to 25,164 tokens (full page text). More tool calls, dramatically fewer tokens.

#### Targeted Extraction (OpenBrowser only)

No equivalent in Playwright or Chrome DevTools MCP -- both require dumping the full snapshot or running JavaScript from the client side.

**Element search** -- the LLM writes Python to find specific elements:

```python
state = await browser.get_browser_state_summary()
for idx, el in state.dom_state.selector_map.items():
    if 'submit' in el.get_all_children_text(max_depth=1).lower():
        print(f"Found submit button at index {idx}")
```

**Data extraction** -- extract specific data via JS evaluation, not full-page dumps:

```python
# Extract only what's needed from a 97K-char Wikipedia page
data = await evaluate('document.querySelector(".infobox")?.innerText')
print(data)  # ~900 chars instead of ~97K
```

#### Why OpenBrowser Uses More Tool Calls but Fewer Tokens

Playwright sends the full page with every response, so the LLM gets the answer immediately but pays for ~120K tokens per Wikipedia page load. OpenBrowser returns compact results (~30-800 chars per call), so the LLM needs more round-trips to navigate and extract but pays far fewer tokens overall.

For a single simple task, Playwright's approach is fast. In the 2026-02-21 six-task run, the ratio of mean total MCP response characters per six-task run, averaged over five runs per server, was 144x. Complex pages drove most of the difference. That ratio is a historical observation, not a current-version guarantee.

### Unique to OpenBrowser

This section describes the benchmarked OpenBrowser v0.1.26 server. The benchmark itself used `execute_code` only. The `get_status` and `reset_browser` lifecycle tools were added after v0.1.26 and were not part of the comparison. The feature bullets below describe the v0.1.26 server. The run measured response size and tool counts; it did not benchmark each feature:

- **CodeAgent architecture** -- the core `execute_code` tool runs Python in a persistent namespace. The LLM writes code to navigate, extract, and process data rather than calling individual tools. Variables and state persist between calls.
- **144x smaller mean total MCP response characters per six-task run in 2026-02-21** -- returns only the data the code explicitly extracts, not full page dumps
- **JS evaluation with Python processing** -- `await evaluate("JS expression")` returns Python objects directly (dicts, lists, strings), enabling pandas/regex/json processing in the same code block
- **Built-in libraries** -- json, pandas, numpy, matplotlib, csv, re, datetime, requests, BeautifulSoup available in the execution namespace
- **File system access** -- `file_system` object for reading/writing local files from browser automation code
- **Dropdown support** -- `select_dropdown()` and `dropdown_options()` for native `<select>` elements
- **Task completion signal** -- `done(text, success)` to explicitly mark task completion with a result

### Provenance and limits

- The 5-step token benchmark was recorded on 2026-02-21 with OpenBrowser MCP v0.1.26. The Playwright MCP and Chrome DevTools MCP resolved versions were not recorded.
- The 6-task LLM benchmark was recorded on the same date with Claude Sonnet 4.6 on AWS Bedrock, 5 runs per server, and a 10,000-sample bootstrap. The retained aggregate is `benchmarks/e2e_llm_stats_results.json`. It records the model, run count, and server aggregates, but not the competitor tool versions or a timestamp. The page date is a page record, not an artifact field.
- The per-response files cited by earlier revisions of this page are not present in the repository. Their numbers cannot be recomputed from the retained files. The tables on this page remain a historical summary, not a reproducible artifact.
- Token volume is not task success, latency, or cost for every workload. The six tasks are a fixed local sample against public sites. Treat differences in tool count and response shape as design tradeoffs, not a universal winner.
- Do not compare these numbers with a later release without a new pinned run. The native navigation harness is a separate lane and is not a source for this page.

### Benchmark Methodology Notes

#### Token Usage Benchmark (5-step workflow)
- All three servers benchmarked via JSON-RPC stdio subprocess -- no estimates
- Response sizes measured as total JSON-RPC response character count
- Estimated tokens = characters / 4 (standard approximation for mixed English/JSON)
- 5-step workflow uses matched operations: navigate, get state/snapshot, click, go back, get state/snapshot
- Raw per-response data for the 5-step run: not retained in this repository. The numbers above are the retained summary.

#### E2E LLM Benchmark (6 real-world tasks, N=5 runs)
- Model: Claude Sonnet 4.6 on AWS Bedrock (Converse API)
- Each task uses a single MCP server as tool provider via JSON-RPC stdio
- The LLM autonomously decides which tools to call and when the task is complete
- 5 runs per server, 10,000-sample bootstrap for 95% confidence intervals
- 6 tasks: fact_lookup, form_fill, multi_page_extract, search_navigate, deep_navigation, content_analysis
- All tasks run against live websites (Wikipedia, httpbin.org, news.ycombinator.com, github.com, example.com)
- Bedrock API token usage measured from the Converse API `usage` field (actual billed tokens)
- MCP response sizes measured from tool response character counts
- Playwright MCP installed from `npx @playwright/mcp@latest` on the run date; the resolved version was not recorded
- Chrome DevTools MCP installed from `npx -y chrome-devtools-mcp@latest` on the run date; the resolved version was not recorded
- OpenBrowser MCP v0.1.26 tested via `uvx openbrowser-ai[mcp]==0.1.26 --mcp`
- All tests run on macOS, M-series Apple Silicon
- Benchmark scripts: `benchmarks/e2e_llm_benchmark.py`, `benchmarks/e2e_llm_stats.py`
- Results: `benchmarks/e2e_llm_stats_results.json`
