## 2. How to read this page

A fixture is a local test page with a deterministic expected result. The current native lanes use fixtures. The historical MCP and CLI sections below use live websites and are labeled separately. A run passes only when the product returns the required result, so every latency number has a correctness check behind it.

| Term | Meaning |
| --- | --- |
| p50 (median) | The middle sample. Half the runs were faster and half were slower. |
| Cold start | Every task starts a fresh process tree, including the daemon or server and the browser. |
| Warm | The browser is already open. Each task gets a fresh fixture page, not a fresh browser. |
| No-browser | No Chromium, Blink, or V8 process. The tool fetches over HTTP and parses the response. JavaScript does not run. |
| RSS | Resident set size: physical memory held by the process tree at the sample time. Shared pages can be counted more than once. |
| Pair | One sample from each arm on the same task and sample index. A 5 of 5 result means OpenBrowser was faster in all five pairs. |
| N | The number of samples per arm and task. |

For task time and memory, lower is better. Charts and tables that measure them carry a down arrow and the label **Lower is better**. If a chart shows a metric where higher is better, it says **Higher is better** with an up arrow.

## 3. Current interactive lanes, 2026-11-25

These lanes use five arms: OpenBrowser MCP, OpenBrowser CLI, chrome-devtools-mcp, agent-browser, and browser-use. Each task runs against a local fixture with an exact oracle. Both lanes use N=5 per arm and task and rotate the arm order.

### 3.1. Cold interactive

The cold lane starts a fresh process tree, daemon or server, and browser for every task. 125 of 125 runs passed the exact oracle and the mock-keychain check. Host load was 6.570, 4.896, 4.404 before and 6.729, 6.016, 4.994 after on 18 logical CPUs. The MCP transport was the lean variant. The host Playwright cache was exposed to every arm.

## 4. OpenBrowser no-browser memory, 2026-11-25

Peak process-tree RSS (MiB) ↓ **Lower is better**.

<img src="/images/native-mcp-http-memory.png" alt="Bar chart of peak process-tree RSS in MiB for one scrape_web call and 25 concurrent scrape_web calls. Both use no browser process." />

The `scrape_web` MCP tool runs without Chromium, Blink, or V8. It performs an HTTP fetch and parses the response. It does not run JavaScript, take screenshots, or use browser cookies. It never falls back to a browser. This is not the same scope as a browser engine. A page that needs JavaScript must use `execute_code` with a browser.

Peak process-tree RSS (MiB) ↓ **Lower is better**.

| Mode | Peak process-tree RSS | Browser processes | Correct results |
| --- | ---: | ---: | ---: |
| One `scrape_web` call | 48.1 MiB median (47.55 to 50.17, N=5) | 0 | 5 of 5 |
| 25 concurrent `scrape_web` calls | 62.4 MiB median (62.31 to 64.30, N=3) | 0 | 25 of 25 in 3 of 3 runs |

Sequential latency was 77 to 90 ms per call after discovery. The 25 concurrent calls completed in 155 to 169 ms. These timings are for one local static fixture and are not a general throughput claim.

### 4.1. Non-comparable context

The following published or earlier figures use different measurement methods and workloads. They are context, not points on the chart, and they are not a direct memory ranking. For memory values, **Lower is better** ↓, but the scopes below are not comparable.

| Reference | Value | Scope | Why it is not comparable |
| --- | ---: | --- | --- |
| Lightpanda, one automation page | 21.2 MB | Published by Lightpanda | Uses its own measurement method, not process-tree RSS on this fixture. |
| Lightpanda, 25 parallel crawler processes | 123 MB | PSS for 25 processes crawling 933 pages on Ubuntu AWS m5.xlarge | PSS on a different host and workload. Our 25-call number is one server process. |
| Firecrawl Local static, earlier local measurement | about 155 MiB | Included the benchmark controller | Our number is process-tree RSS without a controller. |

Our values are process-tree RSS in MiB, divided by 1048576. RSS can count shared pages more than once. Our 25-call number is one server process that handles 25 concurrent calls. Lightpanda's 123 MB is PSS for 25 separate processes. RSS and PSS are not directly comparable.

A single-call comparison with Lightpanda's 21.2 MB is not supported by this lane. No direct memory win against Lightpanda or Firecrawl follows from these numbers.

### 5.3. Render asset policy

Requests, bytes, and scrape time: **Lower is better** ↓. Screenshots are a capability, not a score.

The render mode is a capability preset. The asset flags change only which resource types reach the network, so a caller can keep screenshots and still skip external CSS.

This table comes from a local page with two stylesheets, one web font, 20 images, and 20 JavaScript-rendered headlines. N=10, interleaved. The request and byte columns are exact server observations.

Requests, bytes, and scrape time: **Lower is better** ↓. Screenshots are a capability, not a score.

| Arm | Blocked types | Requests | Bytes | Scrape p50 | Screenshots |
| --- | --- | ---: | ---: | ---: | --- |
| full | none | 25 | 2908 | 44.6 ms | yes |
| lightweight | images, fonts, media, text tracks | 4 | 1336 | 44.6 ms | yes |
| no-render | the four above plus stylesheets | 2 | 1174 | 31.3 ms | no |
| `--text-only` | the same five | 2 | 1174 | 31.6 ms | yes |

Blocking CSS is the scrape-time lever on this fixture: 44.6 ms falls to 31.3 ms. Blocking images alone does not move scrape time because the images are tiny and load in parallel.

Two limits matter. First, blocking external CSS exposes content that the page hides with `display:none` or `visibility:hidden`, which is why Lightpanda's own agent modes keep CSS on. Second, these flags reduce requests and bytes, not Chromium process memory. Use the OpenBrowser no-browser path (`--no-browser` or `scrape_web`) for static pages.

```bash
openbrowser-ai scrape https://example.com --text-only --only-main-content
openbrowser-ai --render-mode full --no-css --no-images -c "await navigate('https://example.com')"
```

<a id="discovery"></a>

### 5.5. Discovery: map and crawl

Firecrawl users build site pipelines on `map` and `crawl`. OpenBrowser has both, and neither starts a browser.

```bash
openbrowser-ai map https://docs.example.com --max-urls 50 --exclude '\.pdf$'
openbrowser-ai crawl https://docs.example.com --max-pages 20 --max-depth 2
```

`map_urls` reads the page, `/sitemap.xml`, and one sitemap index level, then normalizes, deduplicates, and filters by origin, include, and exclude patterns. `crawl_site` follows same-origin links breadth first, fetches each page once, parses it once, and returns page content plus a per-page link count.

Limits: both use the OpenBrowser no-browser path. A JavaScript shell page is reported as a failed or skipped page, not rendered. This section is a functional check, not a timed comparison.

## 6. How to choose a surface

| Need | Use | Why |
| --- | --- | --- |
| One static page, no browser | `openbrowser-ai scrape URL --no-browser` or MCP `scrape_web` | No Blink or V8. JavaScript does not run. See the no-browser memory section. |
| Many known URLs | `openbrowser-ai scrape --no-browser --jsonl` | Concurrent no-browser fetches. |
| Site discovery | `openbrowser-ai map URL` | Page links plus sitemap. No browser. |

### 12.3. Why the Difference

| Design Decision | Playwright MCP | Chrome DevTools MCP | OpenBrowser MCP |
|----------------|---------------:|--------------------:|----------------:|
| Navigate response | Full a11y snapshot | URL confirmation | URL confirmation |
| State query | Always full snapshot | Full a11y snapshot (`take_snapshot`) | Compact (105 tokens) or full |
| Click response | Updated snapshot | Action confirmation | Action confirmation |
| Text extraction | No dedicated tool | No dedicated tool | `evaluate()` + Python processing |
| Content search | Dump full snapshot | `evaluate_script` (JS) | `evaluate()` + Python regex/string matching |
| Element search | Part of snapshot | `uid` from snapshot | `browser.get_browser_state_summary()` |

**Playwright MCP**: Every navigation returns the full page accessibility snapshot (~124K tokens for Wikipedia). Consistent, but forces the LLM to process the entire page with every action.

**Chrome DevTools MCP**: Returns minimal confirmations for navigation. The agent must explicitly call `take_snapshot` to see the page (~135K tokens for Wikipedia). One snapshot is comparable in size to Playwright's, but actions don't auto-return snapshots.

**OpenBrowser MCP**: Actions return minimal confirmations. The agent explicitly requests the level of detail it needs: from 105 tokens (compact state) to 3,981 tokens (targeted search) to 25,164 tokens (full page text). More tool calls, fewer tokens.

#### 12.6.10. Why OpenBrowser Uses More Tool Calls but Fewer Tokens

Playwright sends the full page with every response, so the LLM gets the answer immediately but pays for ~120K tokens per Wikipedia page load. OpenBrowser returns compact results (~30 to 800 chars per call), so the LLM needs more round-trips to navigate and extract but pays fewer tokens overall.

For a single simple task, Playwright's approach is fast. ### 12.8. OpenBrowser features in v0.1.26

This section describes the benchmarked OpenBrowser v0.1.26 server. The benchmark itself used `execute_code` only. The `get_status` and `reset_browser` lifecycle tools were added after v0.1.26 and were not part of the comparison. The feature bullets below describe the v0.1.26 server. The run measured response size and tool counts; it did not benchmark each feature:

- **CodeAgent architecture**: the core `execute_code` tool runs Python in a persistent namespace. The LLM writes code to navigate, extract, and process data rather than calling individual tools. Variables and state persist between calls.
- **144x smaller mean total MCP response characters per six-task run in 2026-02-21**: returns only the data the code explicitly extracts, not full page dumps

- **File system access**: `file_system` object for reading/writing local files from browser automation code
- **Dropdown support**: `select_dropdown()` and `dropdown_options()` for native `<select>` elements
- **Task completion signal**: `done(text, success)` to explicitly mark task completion with a result

### 12.10. Provenance and limits

- The 5-step token benchmark was recorded on 2026-02-21 with OpenBrowser MCP v0.1.26. The Playwright MCP and Chrome DevTools MCP resolved versions were not recorded.
- The 6-task LLM benchmark was recorded on the same date with Claude Sonnet 4.6 on AWS Bedrock, 5 runs per server, and a 10,000-sample bootstrap. The retained aggregate is [e2e_llm_stats_results.json](https://github.com/billy-enrizky/openbrowser-ai/blob/main/benchmarks/e2e_llm_stats_results.json). It records the model, run count, and server aggregates, but not the competitor tool versions or a timestamp. The page date is a page record, not an artifact field.
- The per-response files cited by earlier revisions of this page are not present in the repository. Their numbers cannot be recomputed from the retained files. The tables on this page remain a historical summary, not a reproducible artifact.
- Token volume is not task success, latency, or cost for every workload. The six tasks are a fixed local sample against public sites. Treat differences in tool count and response shape as design tradeoffs, not a universal winner.
- Do not compare these numbers with a later release without a new pinned run. The native navigation harness is a separate lane and is not a source for this page.

### 12.11. Benchmark Methodology Notes

#### 12.11.1. Token Usage Benchmark (5-step workflow)
- All three servers benchmarked via JSON-RPC stdio subprocess, with no estimates
- Response sizes measured as total JSON-RPC response character count
- Estimated tokens = characters / 4 (standard approximation for mixed English/JSON)
- 5-step workflow uses matched operations: navigate, get state/snapshot, click, go back, get state/snapshot
- Raw per-response data for the 5-step run: not retained in this repository. The numbers above are the retained summary.

#### 12.11.2. E2E LLM Benchmark (6 real-world tasks, N=5 runs)
- Model: Claude Sonnet 4.6 on AWS Bedrock (Converse API)
- Each task uses a single MCP server as tool provider via JSON-RPC stdio
- The LLM autonomously decides which tools to call and when the task is complete
- 5 runs per server, 10,000-sample bootstrap for 95% confidence intervals
- 6 tasks: fact_lookup, form_fill, multi_page_extract, search_navigate, deep_navigation, content_analysis
- All tasks run against live websites (Wikipedia, httpbin.org, news.ycombinator.com, github.com, example.com)
- Bedrock API token usage measured from the Converse API `usage` field (actual billed tokens)
- MCP response sizes measured from tool response character counts
- Playwright MCP installed from `npx @playwright/mcp@latest` on the run date; the resolved version was not recorded
- Chrome DevTools MCP installed from `npx -y chrome-devtools-mcp@latest` on the run date; the resolved version was not recorded
- OpenBrowser MCP v0.1.26 tested via `uvx openbrowser-ai[mcp]==0.1.26 --mcp`
- All tests run on macOS, M-series Apple Silicon
- Benchmark scripts: [e2e_llm_benchmark.py](https://github.com/billy-enrizky/openbrowser-ai/blob/main/benchmarks/e2e_llm_benchmark.py), [e2e_llm_stats.py](https://github.com/billy-enrizky/openbrowser-ai/blob/main/benchmarks/e2e_llm_stats.py)
- Results: [e2e_llm_stats_results.json](https://github.com/billy-enrizky/openbrowser-ai/blob/main/benchmarks/e2e_llm_stats_results.json)
