## The question this page answers

A coding agent that needs a browser has to pick one. The choice is usually made on latency alone, but latency is three different things:

1. How fast one page is scraped.
2. How fast one interactive task finishes once a browser is ready.
3. How long a cold start takes before any work begins.

Memory is a fourth axis, and it decides how many agents fit on one machine. This page measures all four on deterministic local fixtures, with exact oracles, so every number has a correctness check behind it.

The short version:

- OpenBrowser wins every sequential scraping task against Firecrawl Local, and 50 of 50 paired samples.
- OpenBrowser wins every warm interactive task against every competitor, 10 of 10 pairs each.
- The cold lane now wins two of five tasks outright and is inside 2 percent on a third. Browser-use still wins click-triggered download and multi-tab work.
- A one-shot static scrape costs 148.6 ms and 47.7 MB of peak memory. A browser scrape costs 355 to 382 MB with the headless shell, against 742 to 755 MB with full Chrome.

<a id="render-policy"></a>

### Render asset policy

The render mode is a capability preset. The asset flags change only which resource types reach the network, so a caller can keep screenshots and still skip external CSS.

This table comes from a local page with two stylesheets, one web font, 20 images, and 20 JavaScript-rendered headlines. N=10, interleaved. The request and byte columns are exact server observations.

| Arm | Blocked types | Requests | Bytes | Scrape p50 | Screenshots |
| --- | --- | ---: | ---: | ---: | --- |
| full | none | 25 | 2908 | 44.6 ms | yes |
| lightweight | images, fonts, media, text tracks | 4 | 1336 | 44.6 ms | yes |
| no-render | the four above plus stylesheets | 2 | 1174 | 31.3 ms | no |
| `--text-only` | the same five | 2 | 1174 | 31.6 ms | yes |
| HTTP-only | no browser | 1 | 1165 | 198.7 ms wall | no |

Blocking CSS is the scrape-time lever on this fixture: 44.6 ms falls to 31.3 ms. Blocking images alone does not move scrape time because the images are tiny and load in parallel.

Two limits matter. First, blocking external CSS exposes content that the page hides with `display:none` or `visibility:hidden`, which is why Lightpanda's own agent modes keep CSS on. Second, these flags reduce requests and bytes, not Chromium process memory. Use the HTTP path for static pages.

```bash
openbrowser-ai scrape https://example.com --text-only --only-main-content
openbrowser-ai --render-mode full --no-css --no-images -c "await navigate('https://example.com')"
```

#### What changed in the cold lane

A cold start is one browser launch plus one server startup. On this host a `BrowserSession.start()` takes about 550 ms, and Chrome accounts for most of it. Four changes removed about 400 ms from the OpenBrowser side:

1. The code-use namespace import runs on a worker thread while Chrome starts.
2. Optional namespace libraries resolve lazily. numpy, pandas, bs4, pypdf, reportlab, and the video recorder no longer load unless a cell uses them.
3. The MCP server answers `server/discover` without the code-use stack.
4. Readiness polls are 20 ms, and a fixed 50 ms redirect sleep is gone.

Cold `openbrowser-ai -c pass` measured 1337.6 ms p50 before this work and 968.7 ms after. A paired N=12 run measured 1234.8 ms to 1019.4 ms with 11 of 12 pairs faster.

<a id="mcp-surface"></a>

#### Why the MCP surface is the one to use

The MCP arm speaks the stateless `2026-07-28` protocol: one `server/discover` probe, then `create_context`, `execute_code`, and `close_context`. Each context owns a browser, a namespace, a profile, and a download path. A coding agent that opens one context and keeps it open gets the warm numbers above.

The MCP arm is faster than the CLI arm on every task because there is no per-call process start and no per-call daemon handshake. The CLI still starts faster than a full server for a one-off command.

### Firecrawl batch scraping

Firecrawl Local exposes a native `/v2/batch/scrape` job API. The comparison sends the same five pagination URLs to both products and checks that each returns the same 100 ordered names. The OpenBrowser arm uses `scrape_pages(engine="http", concurrency=5)` and never starts a browser. The Firecrawl arm submits one batch job, polls it every 10 ms, and downloads the results. All 20 measured runs passed.

| Arm | Samples | p50 ms | p95 ms | Range ms | Requests |
| --- | ---: | ---: | ---: | ---: | ---: |
| OpenBrowser HTTP batch | 10 | 2.834 | 3.389 | 2.503 to 3.389 | 5 |
| Firecrawl Local batch | 10 | 13.448 | 14.013 | 11.961 to 14.013 | 5 |

OpenBrowser was faster in 10 of 10 pairs. The median paired difference was `10.625` ms, and OpenBrowser was 4.75 times faster at p50. No browser started for any OpenBrowser batch. The arms return different artifacts: OpenBrowser returns selected row dictionaries, while Firecrawl returns markdown pages. Both satisfy the 100-name oracle.

<a id="discovery"></a>

### Discovery: map and crawl

Firecrawl users build site pipelines on `map` and `crawl`. OpenBrowser now has both, and neither starts a browser.

```bash
openbrowser-ai map https://docs.example.com --max-urls 50 --exclude '\.pdf$'
openbrowser-ai crawl https://docs.example.com --max-pages 20 --max-depth 2
```

`map_urls` reads the page, `/sitemap.xml`, and one sitemap index level, then normalizes, deduplicates, and filters by origin, include, and exclude patterns. `crawl_site` follows same-origin links breadth first, fetches each page once, parses it once, and returns page content plus a per-page link count.

Limits: both are HTTP-only. A JavaScript shell page is reported as a failed or skipped page, not rendered.

### How to choose a surface

| Need | Use | Why |
| --- | --- | --- |
| One static page, lowest memory | `openbrowser-ai scrape URL` | 148.6 ms and 47.7 MB, no browser |
| Many known URLs | `scrape --engine http --jsonl` | Concurrent HTTP, no browser |
| Site discovery | `openbrowser-ai map URL` | Page links plus sitemap, no browser |
| Site-wide text | `openbrowser-ai crawl URL` | Bounded breadth-first crawl, no browser |
| JavaScript page, one shot | `scrape --engine browser` | Headless shell, 355 to 382 MB |
| Long interactive session | MCP `create_context` plus `execute_code` | Warm numbers above |
| One-off interactive command | `openbrowser-ai -c` | No server to manage |
| Visual work | `--render-mode full` | Screenshots and real paint |

### What these lanes show

OpenBrowser is faster than Firecrawl Local on every sequential scraping task, and 4.75 times faster on the native batch surface. It also ships the discovery primitives, main-content filtering, and asset flags that Firecrawl users rely on.

OpenBrowser is faster than every competitor on every warm interactive task in the paired runs. The MCP arm won 10 of 10 pairs on wizard, modal, tabs, and download, with p50 deltas of 330.5 ms, 519.4 ms, 75.8 ms, and 89.4 ms.

Cold starts are no longer a blanket loss. The MCP arm beats chrome-devtools-mcp on all five cold tasks, agent-browser on four, and browser-use on two, and it is within 2 percent on a third. Download and tabs still belong to browser-use.

Memory depends on the surface, not the brand. The same product costs 47.7 MB for a static page, 355 to 382 MB for a JavaScript page in the headless shell, and 742 to 755 MB in full Chrome.

The fixtures do not test live-site anti-bot behavior, CAPTCHA, or login providers. The resource lane measures RSS and CPU, not GPU memory, disk I/O, or energy. Lightpanda and Chromium use different engines and do not have identical layout, paint, extension, or screenshot behavior. Local fixture results do not establish a ranking for live websites.

### Why the Difference

| Design Decision | Playwright MCP | Chrome DevTools MCP | OpenBrowser MCP |
|----------------|---------------:|--------------------:|----------------:|
| Navigate response | Full a11y snapshot | URL confirmation | URL confirmation |
| State query | Always full snapshot | Full a11y snapshot (`take_snapshot`) | Compact (105 tokens) or full |
| Click response | Updated snapshot | Action confirmation | Action confirmation |
| Text extraction | No dedicated tool | No dedicated tool | `evaluate()` + Python processing |
| Content search | Dump full snapshot | `evaluate_script` (JS) | `evaluate()` + Python regex/string matching |
| Element search | Part of snapshot | `uid` from snapshot | `browser.get_browser_state_summary()` |

**Playwright MCP**: Every navigation returns the full page accessibility snapshot (~124K tokens for Wikipedia). Consistent, but forces the LLM to process the entire page with every action.

**Chrome DevTools MCP**: Returns minimal confirmations for navigation. The agent must explicitly call `take_snapshot` to see the page (~135K tokens for Wikipedia). One snapshot is comparable in size to Playwright's, but actions don't auto-return snapshots.

**OpenBrowser MCP**: Actions return minimal confirmations. The agent explicitly requests the level of detail it needs -- from 105 tokens (compact state) to 3,981 tokens (targeted search) to 25,164 tokens (full page text). More tool calls, dramatically fewer tokens.

**Playwright MCP** `browser_snapshot` -- full a11y tree again (~1,896 chars on httpbin, ~495K chars on Wikipedia):

```yaml
- generic [ref=e2]:
  - paragraph [ref=e3]:
    - generic [ref=e4]:
      - text: "Customer name:"
      - textbox "Customer name:" [ref=e5]
  ... (entire page tree)
```

**Chrome DevTools MCP** `take_snapshot` -- full a11y tree (~1,214 chars on httpbin, ~538K chars on Wikipedia):

```
uid=1_0 RootWebArea url="https://httpbin.org/forms/post"
  uid=1_1 StaticText "Customer name: "
  uid=1_2 textbox "Customer name: "
  uid=1_3 StaticText "Telephone: "
  uid=1_4 textbox "Telephone: "
  uid=1_5 StaticText "E-mail address: "
  uid=1_6 textbox "E-mail address: "
  ... (entire page tree)
```

**OpenBrowser MCP** -- the LLM writes Python code to query exactly what it needs:

```python
# Get page metadata
state = await browser.get_browser_state_summary()
print(json.dumps({"url": state.url, "title": state.title}))
```

```json
{"url": "https://httpbin.org/forms/post", "title": "httpbin.org/forms/post"}
```

The agent requests only the data it needs via Python code -- page title, specific element attributes, or targeted JS evaluation. No full-page dumps.

#### Click / Type / Go Back

All three servers return short confirmations for actions:

| Operation | Playwright MCP | Chrome DevTools MCP | OpenBrowser MCP |
|-----------|---------------|---------------------|-----------------|
| Click | `Clicked element` | `Clicked element uid=1_2` | `Clicked element 5` |
| Type | Updated snapshot (~526 chars) | `Filled element uid=1_2` | `Typed 'John Doe' into element 4` |
| Go back | ~198 chars | ~149 chars | `Navigated back` |

#### Targeted Extraction (OpenBrowser only)

No equivalent in Playwright or Chrome DevTools MCP -- both require dumping the full snapshot or running JavaScript from the client side.

**Element search** -- the LLM writes Python to find specific elements:

```python
state = await browser.get_browser_state_summary()
for idx, el in state.dom_state.selector_map.items():
    if 'submit' in el.get_all_children_text(max_depth=1).lower():
        print(f"Found submit button at index {idx}")
```

**Data extraction** -- extract specific data via JS evaluation, not full-page dumps:

```python
# Extract only what's needed from a 97K-char Wikipedia page
data = await evaluate('document.querySelector(".infobox")?.innerText')
print(data)  # ~900 chars instead of ~97K
```

#### Why OpenBrowser Uses More Tool Calls but Fewer Tokens

Playwright sends the full page with every response, so the LLM gets the answer immediately but pays for ~120K tokens per Wikipedia page load. OpenBrowser returns compact results (~30-800 chars per call), so the LLM needs more round-trips to navigate and extract but pays far fewer tokens overall.

For a single simple task, Playwright's approach is fast. In the 2026-02-21 six-task run, the ratio of mean total MCP response characters per six-task run, averaged over five runs per server, was 144x. Complex pages drove most of the difference. That ratio is a historical observation, not a current-version guarantee.

### Unique to OpenBrowser

This section describes the benchmarked OpenBrowser v0.1.26 server. The benchmark itself used `execute_code` only. The `get_status` and `reset_browser` lifecycle tools were added after v0.1.26 and were not part of the comparison. The feature bullets below describe the v0.1.26 server. The run measured response size and tool counts; it did not benchmark each feature:

- **CodeAgent architecture** -- the core `execute_code` tool runs Python in a persistent namespace. The LLM writes code to navigate, extract, and process data rather than calling individual tools. Variables and state persist between calls.
- **144x smaller mean total MCP response characters per six-task run in 2026-02-21** -- returns only the data the code explicitly extracts, not full page dumps
- **JS evaluation with Python processing** -- `await evaluate("JS expression")` returns Python objects directly (dicts, lists, strings), enabling pandas/regex/json processing in the same code block
- **Built-in libraries** -- json, pandas, numpy, matplotlib, csv, re, datetime, requests, BeautifulSoup available in the execution namespace
- **File system access** -- `file_system` object for reading/writing local files from browser automation code
- **Dropdown support** -- `select_dropdown()` and `dropdown_options()` for native `<select>` elements
- **Task completion signal** -- `done(text, success)` to explicitly mark task completion with a result
